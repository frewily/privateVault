# PrivateVault 技术可行性研究 02：来源适配与 Android 下载运行环境

日期：2026-10-25（Asia/Shanghai） · 版本：v0.1

依据：根目录《PrivateVault-需求与架构设计-v0.2.md》与《01-三端本地OpenList复用可行性-v0.1.md》。

状态：**完成本轮公开工具支持范围、关键源码与 Android 运行时的研究；完整双来源可行性尚未闭合，运行验证未执行。** 本次仅新增本文，未安装、运行、构建下载工具，未登录来源站，未读取用户凭证，未访问作品或视频内容，未下载媒体，未连接百度网盘，未写实现代码或提交/推送。

## 1. 结论与建议

本轮将“网站解析”“下载运行环境”“归档与云端提交”分开判断。

| 对象 | 已获得的依据 | 当前结论 |
|---|---|---|
| Pixiv 静态图片作品 | gallery-dl 明确列出支持；有单作品解析、图片页列表、基础元信息和令牌认证路径 | **优先复用的来源候选，有明确源码基础，待授权与样本运行验证** |
| hanime1 视频来源 | 本次核对 gallery-dl/yt-dlp 支持列表，未找到对应条目；yt-dlp 默认分支一次代码搜索无结果 | **未证实支持，保留目标，不承诺现成工具开箱即用** |
| Android 运行 Python 图片适配器 | Chaquopy 提供 Android 内嵌 Python、Java/Kotlin 桥接和依赖打包方式 | **具备可评估的宿主路线，不等于 gallery-dl 已在项目手机上运行通过** |
| Android 通用视频下载引擎 | youtubedl-android 有初始化、进程执行、取消、元信息映射及原生组件封装 | **可复用候选；引擎存在不证明 hanime1 适配成立** |

建议：

1. Pixiv 首个验证范围以单个静态插画/漫画作品为主；同一作品可能有多张图片。动图单列，不默认转换。
2. 优先让成熟工具完成来源解析和下载到受控工作区，再由 PrivateVault 执行校验、按库模式上传及元信息提交。先避免复制整套来源逻辑。
3. Android 优先评估“自有宿主＋显式选择 Python 版本的嵌入环境＋受控 gallery-dl 适配”；通用视频引擎另设能力边界，不预先承诺两个 Python 封装可以混用。
4. 不因某个来源尚不确定而取消三端独立归档目标；也不把某端调用中心 Mac 代执行，当作通过 Android 本机归档验收。
5. 当前不能冻结“两个来源均已支持”的首版承诺。下一项仍需研究百度授权/Crypt/Range，再将所有未闭合项汇总为最小验证计划。

## 2. 研究范围、方法与限制

本轮只读检查工具项目官方仓库的支持列表、依赖、来源解析器、认证交互、任务接口，以及 Android Python/视频工具封装文档与源码。官方工具仓库是该工具行为的一手来源，**不等于来源网站官方认可其所有访问方式**。

没有进行：

- 作品/视频页面访问、真实资源地址提取或媒体请求。
- 用户账号、OAuth、Cookie、刷新令牌的读取、导入或授权。
- 安卓包、Python 二进制、wheel、FFmpeg 或运行时的下载/构建/执行。
- 来源站服务条款的完整当前核验。读取 Pixiv 官方公开条款入口的浏览器请求未成功取得可核对内容，因此不作已读或许可已确认的结论。

hanime1 本轮仅核查通用工具支持状态，不提供内容定位、专用资源提取或下载操作。没有足够证据判断其网站端访问、授权、提取和格式是否符合项目要求，不将未核实的接口作为方案基础。

证据等级：**源码事实**、**设计建议**、**待核实**、**待运行验证**。以下各类结论不能互相替代：工具列出支持、合法授权、源码路径存在、实际下载成功、三端打包成功、云端归档完成。

## 4. Pixiv：单作品与基础元信息有直接复用依据

### 4.1 支持范围

gallery-dl 支持列表列出 Pixiv 作品等入口；本轮重点阅读 PixivWorkExtractor，它将单作品交给作品详情读取路径。Pixiv 图片页解析对多页作品生成多项图片记录。[S1][S2]

这支持 v0.2 的“先单个作品链接跑通”。首版入口应限定已同意的单作品范围，不因为工具同时支持作者页、收藏夹或推荐作品就自动展开下载。

单个作品与单个文件不是同一概念。**设计建议**：一条作品记录关联多个图片 Asset，保留页码/顺序；同一作品是否默认收齐全部图片，在验证计划中明确，不隐式只存第一张或自动扩展到其他作品。

### 4.2 能保留哪些资料

所查源码处理作品 ID、标题、作者信息、标签、创建时间、图片尺寸、页数等字段，并将作品级与文件级数据输出给任务层。[S2]

建议映射：

| PrivateVault 字段 | 来源候选 | 注意事项 |
|---|---|---|
| source_id / external_id | 来源类别＋作品 ID | 作为来源幂等依据，不能仅靠文件名 |
| source_title | 来源作品标题 | 用户修改后的显示标题独立保留 |
| author | 来源作者 ID、名称/账号字段 | 名称可改，不以名称代替稳定标识 |
| source_tags | 来源原始/翻译标签 | 与用户自定义标签区分，保留来源 |
| source_created_at | 来源创建时间 | 与归档时间、文件时间分别记录 |
| Asset 顺序 | 页码/文件序号 | 多图作品保持顺序，不把最后一页的字段覆盖全作品 |
| 尺寸/扩展名/大小 | 来源描述＋本机文件探测 | 来源声明与实际校验分开，缺字段允许为空 |
| 封面 | 已取得的授权媒体生成，或来源提供的可用封面 | 仍按所属库模式保存；不把明文封面旁路留在加密库外 |

不保证每项作品都提供完整字段。来源说明/标题属于不可信文本，展示前应处理，不能直接执行其中 HTML 或脚本。图片地址、请求头、Cookie 和令牌不属于应公开展示的作品元信息。

### 4.3 静态图片与动图区分

Pixiv 解析器包含 Ugoira 分支、帧数据和归档处理；README 将 FFmpeg 列为 Ugoira 转换的可选依赖。[S2][S4]

据此不能把动图当作普通 JPEG/PNG 路径已经完成。建议先验证静态插画/漫画；动图原始帧/归档保留、预览格式和转换行为后续设计。用户已选择首版不自动转码，不应悄悄启用动图转视频等处理。

## 5. Pixiv 授权：现成工具交互尚不是完整移动登录 SDK

### 5.1 凭证与刷新路径

所查 PixivAppAPI 从配置或缓存取得 refresh-token，并将其用于获取访问令牌；没有刷新凭证时进入认证错误路径。README 将 Pixiv 列入工具的 OAuth 支持范围。[S3][S4]

可以确认工具存在令牌认证处理。不能据此承诺：

- 用户无来源账号/授权也能读取所有作品。
- 登录 PrivateVault 自动等同来源站已授权。
- 相同令牌跨设备永久有效，或不会触发过期、撤销、限流和重新授权。
- 工具项目内建的应用身份与请求方式已获得项目所需的第一方 API 授权保证。

本轮没有取得任何实际令牌，也未复现登录。源站的内容可见性与权限限制应被尊重；项目不能把针对限制的备用逻辑当作无条件成功的保证。

### 5.2 现成 OAuth 交互的产品差距

工具的 OAuthPixiv 代码包含浏览器交互及一次性代码输入，并会将取得的刷新凭证输出/写入工具缓存。[S5]

这说明“把 gallery-dl 放进 Android”还不能直接获得符合 PrivateVault 体验的完整来源登录界面。桌面命令行交互、浏览器打开和输入处理，需要替换或适配为用户控制的授权流程；本稿不提供凭证提取步骤。

PrivateVault 适配必须做到：凭证进入受保护存储，而非普通日志、控制台回显、作品 JSON 或备份包；授权失败应进入 WAITING_AUTH，不无限重试。不在应用里记录用户来源密码，也不默认读取其他 App 的私有 Cookie 数据。

### 5.3 与独立 PrivateVault 账号的衔接建议

在确认允许的来源授权途径后，可优先评估：用户在桌面完成首次来源授权，由可信 PrivateVault 服务受控保存来源配置，其他已登录设备恢复必要凭证，在本机使用。这与用户接受的可信服务端和减少重复设置的目标相符。

这只是候选，不是已经完成的授权产品方案。需要核查来源凭证是否允许/能够多端使用、如何刷新、谁可修改、失效后如何提示。Android 首次独立授权可以另行完善；不要因此将 Android 日常解析/下载转移到 Mac。

## 6. hanime1：支持目标保留，现成适配尚未确认

本次成功读取的 yt-dlp 支持列表未匹配 hanime/hanime1，gallery-dl 列表也未找到 hanime1。对 yt-dlp 默认分支的单次代码搜索未返回 hanime1 结果。[S1][S6]

yt-dlp 自己说明未列出的站点可能被通用或嵌入提取覆盖。因此正确结论是：**缺少已确认的专用支持依据**；不能推导“一定不支持”，也不能推导“通用提取一定可以”。[S6]

本轮没有检查作品页、播放器脚本、媒体地址或登录状态，也未运行提取器。下列事项仍未证实：可用的访问与授权方式、单视频识别、元信息完整度、媒体格式、地址有效期、下载及 Android 行为。

项目处理建议：

- 在目标清单保留该来源，状态标为待研究/验证，不标为可用。
- 不用其他相似名称的站点或现成工具的同类支持代替该域名的证据。
- 不默认复用未核实、未维护或来源不明的专用脚本。
- 通用视频引擎和 SourceAdapter 接口可以继续设计；不会因此自动得到该来源支持。
- 若没有足够依据，完整“双来源首版”的来源门槛仍未通过；不得通过去掉该门槛来宣称全部可行。

当前允许继续推进普通本地视频的加密上传与播放链路设计，作为存储/播放基础验证；它与来源站自动归档是否可用分别记录，不替代用户指定的视频来源目标。

## 7. 桌面端运行与接口复用

gallery-dl 在所查 setup.py 声明 Python ≥3.8、核心依赖 Requests；本次 yt-dlp pyproject.toml 声明 Python ≥3.11。[S4][S7]

建议首个桌面验证采用固定版本工具、独立任务工作区和明确的参数预设。PrivateVault 保留自己的任务状态，不将用户输入直接拼接到命令字符串，也不开放任意工具参数或执行后处理脚本。

gallery-dl 有 DownloadJob、DataJob 等任务类型及结构化消息处理；这些提供封装机会，但不是工具对外承诺永久稳定的 SDK。其配置模块使用进程内全局配置，多任务/多凭证调用不能先假定线程安全。[S8]

| 使用方式 | 优点 | 代价/建议 |
|---|---|---|
| 工具负责解析与下载 | 保留其请求会话、重试、格式及来源处理，减少首版复制逻辑 | 适配进度、取消、工作区、错误和敏感输出；优先验证 |
| 只解析为下载计划，再交本机传输模块 | 与平台任务/缓存控制更紧密 | 必须保留请求上下文、期限和重解析规则；不只传一个 URL |

下载成功只代表本地文件取得；加密上传、远端验证和资料提交仍由 PrivateVault 独立确认。工具本地下载历史不能直接当作“已归档到网盘”的跨端成功记录。

## 8. Android：嵌入 Python 有现成路线，默认值不能直接拼接

### 8.1 Chaquopy 候选

Chaquopy 官方仓库说明其提供 Android Gradle 集成、Python 依赖打包和 Java/Kotlin 调用 Python 的能力。Android 文档列出最低 API、ABI、解释器版本和依赖限制。[S9][S10]

与第一项研究的 Android OpenList 宿主组合，可形成如下**设计候选**：

PrivateVault 界面 → Android 原生宿主 → Python 来源/下载适配 → 本机受控工作文件 → 本机 OpenList AAR → 百度网盘。

这保留三端独立目标，不要求手机把媒体交给 Mac。Go 核心库和 Python 运行时是不同组件，是否能在目标宿主、ABI 和资源预算内可靠共存仍须构建与真机验证。

### 8.2 版本约束

| 组件 | 本次源码/文档要求 | 对项目的影响 |
|---|---|---|
| gallery-dl | Python ≥3.8；Requests 为核心依赖 | 比较适合先评估静态图片路径，但网络、证书和依赖仍待测 |
| yt-dlp 调查快照 | Python ≥3.11 | 不可仅根据旧资料用 Python 3.8/3.10 作为共同运行时 |
| Chaquopy 文档默认值 | 默认 Python 3.10，同时提供更高版本选择 | 如果共用本次 yt-dlp，必须显式选择满足要求的版本 |
| Chaquopy 当前文档最低 Android API | 24 | 不沿用 OpenList Mobile minSdk 21 就承诺整个产品支持同一范围 |
| Chaquopy ABI | Python 3.11 及以前与 3.12 以后支持范围不同 | 对目标手机架构和可选运行时逐项选择，不能默认所有 ABI 都支持 |

这些是固定提交的源码文档状态，未核对具体 Maven 已发布包是否与 main 完全一致。初步可以将 Python 3.11+ 作为共同环境评估起点，但不在没有依赖/设备结果时冻结最终版本。[S7][S9]

### 8.3 依赖不等于全部可直接打包

Chaquopy 文档支持大量纯 Python 包和一部分原生组件包，不代表任意桌面 wheel 都可以复制到 Android。[S9]

建议先采用验证所需的最小依赖集合。图片下载的可选动图转换、复杂 TLS/浏览器组件、视频后处理等按来源真实需要分别引入；不能把视频工具对其他网站的推荐依赖全部当作 Pixiv 首版必需项。

Python 中执行网络请求需离开 UI 主线程；取消、超时、进程终止和恢复必须由本地任务层协调。嵌入解释器存在不等于 Android 自动给予额外后台时间；第一项报告的生命周期约束继续适用。

## 9. Android 通用视频引擎：封装可以参考，不能补出缺失的来源支持

youtubedl-android 的 README 和源码提供初始化、请求构建、子进程执行、进度/输出、取消及元信息映射的包装；其 Kotlin 实现设置 Python 与原生组件的运行环境。[S11]

可以确认有 Android 承载 yt-dlp 的工程路径。它不能证明本项目选定的网站可以解析，也不能自动提供 PrivateVault 的幂等、跨端归档记录和空间配额。

本轮发现的版本证据差异：README 仍有“打包 Python 3.8”的说明，而本次 yt-dlp 要求 Python ≥3.11；旧的 Python 构建说明还出现更早版本示例。实际二进制未下载或检查，因此不能断定此包装当前一定不兼容，也不能直接采用旧说明承诺兼容。[S7][S11]

该包装的 build.gradle.kts 最低 API 为 24。最终使用哪一个发布包、内置解释器/yt-dlp/原生组件版本、ABI、取消与更新行为，需要在批准后的验证中核对。

**设计建议**：把它作为通用视频引擎的备选整合路径。若图片侧已选 Chaquopy，不默认再堆入另一套完整 Python；比较共用运行时和独立封装的维护成本、内存/安装体积、依赖冲突及进程隔离需求后再定案。没有现成公开契约保证两个封装的内部目录或解释器可以直接互用。

## 10. 不转码与必要媒体处理的边界

用户已确认首版不自动转码。这个要求仍保留。

通用视频引擎的 README 说明，分离音视频合并及部分后处理可能需要 FFmpeg/ffprobe；这与是否重新编码不是同一个问题。[S7]

因此后续需要分别描述：

- 原样保留已得到的可播放文件。
- 分片或独立音视频的下载完成与封装/合并。
- 改变编码、分辨率或码率的转码。

前两类是否成为某个合法来源的必要步骤，取决于该来源实际输出；本轮不假定 hanime1 的格式。首版不自动启用转码，不对已有云端原文件做隐式修改。需要的合并/封装能力及存储峰值，在具体来源得到证据后再细化确认。

## 11. 来源适配器与任务契约建议

本节为逻辑设计，不是实现代码或实际可调用的新接口。

### 11.1 输入与解析结果

输入：用户来源链接、目标 vault_id、当前设备、来源凭证引用、质量预设及有限的任务选项。

解析结果建议包含：来源类别、规范作品 ID、媒体类型、作品级资料、Asset 列表/顺序、可用尺寸/格式、预期大小（可未知）、必要处理声明及来源版本。请求上下文另存短期的受保护部分，不能混入公开作品资料。

| 内容 | 建议归属 |
|---|---|
| 作品 ID、来源标题、作者、标签、页序 | 可持久化来源元信息，按资料库模式保存 |
| 刷新令牌、Cookie、授权头 | 凭证存储与短期受控调用，不写作品 JSON/普通日志 |
| 有效期短的媒体地址 | 下载会话上下文，必要时重新解析，不作为永久文件标识 |
| 工具版本、来源适配版本、解析时间 | 任务诊断与兼容性记录，避免升级后无法定位差异 |
| 本地完成文件、大小/校验、格式探测结果 | PrivateVault 后续加密/上传阶段输入 |

只把图片/媒体 URL 交给一个通用下载器，可能丢掉来源所需会话与请求头；这需要专项适配。解析器内部可变数据也要转换为自己的稳定描述，不能依赖某个工具对象一直存活。

### 11.2 错误、恢复与幂等

- 无对应适配：明确不支持/待支持，不无限重试通用提取。
- 缺失、过期或撤销授权：WAITING_AUTH，用户介入后重试。
- 内容不可见或权限不足：保留原因，不把限制视为需要绕过的技术故障。
- 网络/限流：按错误类型退避；不通过无限并发提高重试压力。
- 地址变化或来源版本变化：重新解析并核对，不拼接不同版本内容。
- 工具下载完成：仅推进本地阶段；远端验证和元信息提交后才记录归档成功。
- 同一作品多图：逐 Asset 保存完成状态，作品是否完整单独判断，不能第一张成功就标全成功。

来源幂等候选键为站点＋作品 ID＋源版本/质量；本机工具历史与跨端云端归档记录分开。指定订阅设备切换时不能依赖旧设备私有下载历史决定是否已归档。

## 12. 秘密、许可与分发约束

### 12.1 秘密与授权

来源认证与 PrivateVault 账号、百度授权、Crypt 密钥分别管理。用户接受可信服务器代管秘密，不等于允许把它们存到普通资料区或诊断日志。

gallery-dl 的 OAuth 交互及缓存需要适配敏感输出处理；不用含真实凭证的命令行参数、普通配置备份或控制台回显作为集成方式。服务器下发必要来源凭证的范围、过期处理和设备撤销语义沿用 v0.2 的待设计项。

本轮无法确认 Pixiv 当前服务条款或任一作品的归档许可；没有对合法性作肯定结论。实际样本应由用户自有或取得适当授权。工具所支持的访问方式与具体内容的复制许可分别确认，不提供绕过登录、付费访问、DRM 或内容可见性限制的方案。

### 12.2 许可证组合影响选型

本次 gallery-dl setup.py 声明 GPL-2.0-only，yt-dlp 项目元信息声明 Unlicense，Chaquopy 主许可证为 MIT 文本，youtubedl-android 主许可证为 GPL-3.0 文本。[S4][S7][S12]

结合第一项报告的 OpenList AGPL-3.0，后续必须检查实际嵌入、修改、进程调用、打包及分发组合；尤其不能直接宣称 GPL-2.0-only 组件与 AGPL-3.0 核心放入同一个产品后没有组合问题。进程分离也不自动构成法律结论。

本轮仅识别选型约束，未完成完整许可证审查，也不要求为个人只读研究提前发布代码。原生依赖与最终二进制还需单独列清单。

## 13. 候选方案比较

| 路线 | Pixiv 静态作品 | 视频来源 | Android 主要成本 | 当前建议 |
|---|---|---|---|---|
| 桌面工具进程；Android 嵌入 gallery-dl；视频适配独立 | 明确源码基础 | hanime1 仍未证实 | Python 打包、首次授权、任务生命周期 | **优先做可行性验证的候选** |
| 三端共用 Python 来源层，Android 通过可选 SDK 承载 | 减少来源解析重复维护 | 取决于源支持及视频依赖 | 共同运行时、原生依赖、取消与隔离、许可证组合 | 可继续评估，不能只凭最低 Python 版本定案 |
| 用 Dart/Kotlin/Go 重写来源适配 | 可按统一契约设计 | 同样须核实目标来源 | 维护来源变化、认证和格式逻辑，重复工作较多 | 作为工具复用受阻时的替代评估，不先全部重写 |
| 所有来源交给中心服务器执行 | 可降低客户端适配负担 | 仍不解决来源支持缺口 | 改变三端独立归档要求 | 不作为用户已确认目标的默认替代 |

暂不拍板最终 UI 框架。Flutter＋Android 原生桥接仍有首项研究依据；本项增加了 Python 及依赖组合条件，不能把“Flutter 能调用 Kotlin”当作下载适配全链路已通过。

## 15. 本轮仍未闭合的问题

1. Pixiv：允许的产品化授权方式、Android 首次独立授权、凭证多端使用、实际下载/元信息行为。
2. hanime1：专用/通用工具支持及访问授权均未证实；本轮没有网站内容层面的结论。
3. Android：具体手机、系统与 ABI 未提供；运行时、依赖版本及可接受安装体积/耗电待测。
4. 媒体处理：哪些合法来源需要必要的封装/合并，首版具体范围待定。
5. 开源组合：最终进程与宿主结构下的许可证义务需进一步审查。
6. 百度端到端：本项未验证上传、Crypt、Range 和账户 API，不能以来源研究代替。

这些是可明确定位的研究/验证缺口，不应写成“所有功能已可用”。
