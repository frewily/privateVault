# PrivateVault 技术可行性研究 03：百度授权、Crypt 上传与 Range 链路

日期：2026-10-25（Asia/Shanghai） · 版本：v0.1

状态：**完成本轮关键源码链路研究；百度第一方当前约束及账户端到端行为未确认，运行验证未执行。** 本次仅新增研究文档，未安装、构建、运行 OpenList，未登录/授权百度，未读取凭证、上传、下载媒体或编写实现代码。

依据：项目 v0.2 设计及前两项研究。核心调查固定于 OpenList commit `25e4eb663ffb73991a68d85df4f690d48ad137a6`（本次解析的 v4.2.8）；Crypt 底层对照 rclone v1.75.1 的文件加密源码。

## 1. 结论先行

**百度访问、Crypt 加密上传及范围解密之间有完整可追踪的源码连接，可以继续以此作为最小验证候选；不能据此宣布用户账户与三端播放已通过。**

本轮发现的主要约束：

1. 百度驱动既有直接向百度刷新令牌的路径，也有调用可配置刷新 API 的路径。凭证信任边界必须明确，不能只写“OpenList 自动授权”。
2. 驱动刷新凭证后会更新本机存储配置。独立 PrivateVault 账号的配置同步需要处理凭证版本，不能用服务端旧配置反复覆盖设备新凭证。
3. Crypt 流交给百度驱动时可能需要完整密文暂存，再计算分片哈希上传。不能把流式加密当作无需完整暂存的证明。
4. 所查百度上传进度 helper 是配置了 20 分钟过期的内存缓存，不是跨进程持久化恢复记录；重新加密又会生成新的文件随机量。首版宜承诺原设备恢复或重试，不承诺任意崩溃后从原字节继续。
5. Range helper 对不支持范围的上游有“从头读取并丢弃前缀”的兼容路径。本地返回 206 不足以证明云端高效随机读取，必须同时测冷缓存拖动耗时与实际流量。
6. Crypt 默认文件名/目录加密参数并不等同于 PrivateVault 的“完整加密库”目标；新库需要明确配置，已有库必须匹配既有配置。

## 2. 本轮证据与未确认边界

使用证据：百度驱动初始化、认证刷新、下载链接、上传与校验；Crypt 驱动的配置、加密/解密；上传进度 helper；HTTP 内容服务与范围读取 helper；rclone 加密实现。[S1—S11]

尝试读取百度网盘开放平台文档入口时，本环境请求因域名解析失败未取得内容。**这不代表百度官网宕机，也不能作为任何账户限制的证据。** 本轮未绕过网络限制或配置代理，未取得百度第一方当前授权、文件上限、分片时限、速率及 Range 保证。

源码中的客户端超时、缓存时间、会员分类与分片策略，均是客户端实现行为，不直接等于百度平台最新规则。用户已有 6TB SVIP 不证明剩余容量、应用资格、API 全部权限或任意网络速度。

## 3. 普通库与加密库的链路

普通库：当前设备文件/下载完成文件 → 本机 OpenList 百度驱动 → 百度网盘。

加密库上传：当前设备明文 → 本机 Crypt 加密流 → 百度驱动需要的缓存/分片与哈希 → 百度网盘密文对象。

加密库播放：播放器明文范围请求 → 本机内容服务 → Crypt 计算需读取的密文范围 → 百度驱动提供链接/请求头 → 云端读取 → 本机解密 → 播放器。

以上均不要求媒体通过 Mac 或中心账号服务器转发。账号服务器属于可信配置/密钥服务，不因此自动成为每次媒体读取的执行节点。每台设备实际授权和配置必须有效。

## 4. 百度授权与刷新路径

### 4.1 直接刷新与可配置刷新服务

源码中，直接刷新路径使用百度 OAuth token 端点，携带该存储的应用标识、应用秘密和刷新令牌；缺少所需字段会返回错误。[S1]

另一路径在启用相应选项且配置了刷新 API 地址时，将刷新凭证发送给该地址，并接收新的访问/刷新凭证。[S1]

设计约束：

- 区分百度、PrivateVault 可信服务、OpenList 运行设备，以及可能存在的其他刷新服务。可配置 API 不是天然等于百度第一方服务。
- 实际授权前列清凭证发给谁、应用身份和作用范围；不默认借用来源不明的应用秘密。
- 初始取得刷新令牌的方式、用户应用资格、可用授权范围及失效条件仍需查证，不能用“刷新函数存在”代替首次授权流程。
- 不把源码中的 token 端点或请求字段写成让用户现在粘贴凭证执行的操作；当前仅研究。

### 4.2 本机刷新与中心配置同步

刷新成功后，驱动更新自己的访问令牌和刷新令牌，并保存本机存储配置。[S1]

这与 v0.2 的自动恢复配置需要衔接：

- 中心配置保存凭证版本，设备更新凭证后有受控回传或对账规则。
- 新设备取得的凭证不能只依赖某次旧配置快照。
- 不能默认所有设备可永久复用同一个刷新令牌；多端同时刷新、令牌轮换和失效行为待实际授权验证。
- 不能为了统一刷新而要求已配置设备每次都连接睡眠中的 Mac；具体采用独立设备授权、受控凭证同步或其他方式，由验证证据决定。

用户已接受“一个 PrivateVault 账号尽量恢复配置”的体验目标，这不是无需来源/网盘授权约束的保证。

## 5. 上传：完整暂存是当前实现中的实际分支

### 5.1 Crypt 到百度驱动

Crypt 上传调用 EncryptData，建立加密后的新流，再交给底层存储。百度 Put 先尝试快速上传；如果没有成功且输入没有可复用的文件缓存，它创建临时文件，将流完整读入并计算文件/分片哈希，之后才发起预上传及分片写入。[S2][S3]

**源码事实**：这是明确的完整暂存分支，不仅是“理论上可能有缓存”。

**设计推断**：对于 Crypt 新生成、不可随机读取的加密流，存在走该密文暂存分支的直接依据。实际 HTTP 上传入口、外层缓存及具体版本组合是否还产生其他临时副本，须运行测峰值，不能先假定只有一份。

建议空间模型：原始下载/接收文件＋必要处理输出＋密文暂存＋其他工具缓存＋安全余量。用户本机源文件可能不位于工作区，但不能因为它已存在就忽略新增密文空间。手机大视频尤其需要先预留再执行。

### 5.2 上传完成与清理

驱动流程包含预上传、按块写入、最终创建对象；成功后清理上传进度。其临时文件通过 defer 关闭/删除，错误返回也可能触发清理。[S2]

这不能直接提供 PrivateVault 所需的稳定密文跨重启恢复能力。PrivateVault 必须登记任务源、阶段和校验状态；不能把驱动内部临时路径当作永久恢复资产。

归档完成至少区分：本地文件取得、云端对象创建、远端验证、资料记录提交和其他设备可见。底层进度到 100% 不自动表示全部完成。

## 6. 恢复：已有分片逻辑不等于跨进程无损续传

### 6.1 helper 的实际保存方式

所查百度 Put 使用的 SaveUploadProgress/GetUploadProgress helper 来自进程内缓存，写入设置 20 分钟过期。其键包含驱动名及调用者传入字段；百度调用中传入访问令牌和内容 MD5。[S2][S4]

因此：

- 核心进程结束后，不能将该 helper 当作仍存在的持久化检查点。
- 凭证变化或密文内容变化，会影响进度匹配。
- uploadid 过期时，驱动明确重新预上传并重传分片。
- 这只是所查百度路径的结论，不能外推 OpenList 所有 multipart、任务或其他驱动都没有持久化能力。

### 6.2 Crypt 随机量的影响

对照 rclone v1.75.1，常规 EncryptData 创建新的加密器，并从随机源取得文件 nonce。对相同明文再次常规加密，不能假定生成完全相同的密文。[S5]

把旧上传会话与新一轮加密分片混用会破坏内容一致性。即使驱动在同一进程内保留过进度，也不能由此承诺每次重试均复用原密文身份。

### 6.3 首版建议

采用用户已接受的语义：**原设备保留可靠的阶段状态；能恢复就恢复，否则重做当前文件阶段。** 明确提示重试可能重新加密和重传，不在 UI 中承诺已持久化到某个字节位置。

若后续大文件成本要求严格的跨重启字节续传，再评估稳定密文工作文件＋持久上传状态。那会改变暂存、清理和加密层边界，必须另行设计；不能把已加密文件再送进 Crypt 上传而形成双重加密。

## 7. 下载链接、请求头与代理位置

所查官方下载分支请求文件元信息和下载链接，执行携带百度 User-Agent 的请求，并返回包含 User-Agent 的 Link；为 Link 设置一小时的本地过期值。[S6]

这个一小时是驱动配置的链接缓存/过期标识，不是百度服务端保证任一实际链接至少或恰好有效一小时。提前失效、重定向和重新解析都要验证。

普通浏览器或外部播放器不一定能附加所需请求头；加密库还需要在本地解密。建议统一由当前设备的本地内容服务承接云端请求和必要头处理，给 UI/播放器提供受控本地访问方式。

Crypt 配置声明 OnlyProxy、NoLinkURL 等行为，代理/内容层对 RangeReader 输出提供 HTTP 服务。这是本机代理式解密的源码依据，不需要把解密集中到 Mac。[S3][S7]

不把带令牌或签名的云端链接写进永久作品记录、普通日志或可分享地址。外部播放器仍需测试本机地址、签名/会话、后台存活和格式兼容。

## 8. Range：本地 206 与云端高效范围读取必须分开验收

### 8.1 三层范围语义

1. 播放器请求明文字节范围。
2. Crypt 按加密块边界计算上游范围，读取文件头和对应密文块后解密。[S3][S5]
3. 百度实际下载端点能否正确、有效率地响应这些范围，要通过真实授权链路确认。

内容服务可以根据 RangeReader 生成自己的 206、Content-Range、Content-Length 及 416 等响应。[S7]

### 8.2 兼容回退为什么会造成假象

所查 Range helper 处理上游返回 200 的情况：在没有获得预期范围响应时，它调用 GetRangedHttpReader。后者从完整流读取并丢弃 offset 之前的内容，然后返回所需区间。[S8]

由此可能出现：播放器拿到正确的数据/本地范围响应，但拖动到后段仍要消耗大量前缀下载。它是兼容读取，不代表满足 PrivateVault 的在线随机快进目标。

### 8.3 必须同时观察的证据

- 明文首段、中段、尾段和跨加密块读取，与原样本逐字节一致。
- HTTP 206/416、Content-Range 及明文总长度正确。
- 冷缓存拖到接近尾部的首字节等待及实际云端入站流量，不先下载整个前缀。
- 同一文件普通读取和 Crypt 读取分别测，避免将编码、容器索引和解密问题混为一谈。
- 链接失效后重新取链并恢复当前请求，不因短期 URL 变化破坏媒体身份或验证依据。

网页可以打开、视频开始播放、缓存后拖动流畅、或者单独看到 206，都不能替代上述组合证据。

## 9. 校验、空文件与会员限制

### 9.1 完整性

百度驱动的对象转换没有将返回 MD5 放入通用 HashInfo，源码注释说明不依赖该值。[S9]

因此本项目不应仅用“返回了一个 MD5”“对象存在”证明文件完整。加密对象的哈希也不能直接与明文哈希比较。

建议先对少量用户自有样本执行完整读回、解密并比对明文 SHA-256。实际大库的完整/抽样/仅长度验证策略后续确认，界面记录真实 verified_level，不把抽样验证标成整文件验证。

### 9.2 空文件

当前百度驱动 Put 明确拒绝输入大小小于 1 的流，这是所查驱动行为。Crypt 对空明文生成含格式头的密文，逻辑空文件的组合行为另测；不要把普通空文件与加密后输入大小混为同一个用例。[S2][S5]

### 9.3 会员与超时

源码会读取用户信息里的会员分类，并据此选择分片策略；也包含上传线程、分片超时及重试设置。[S1][S10]

这些不是已经确认的用户 API 权限或最大文件承诺。尤其驱动的客户端超时、缓存过期时间不能当作百度第一方接口时限。账户实际限制、剩余容量和可用速率，留待第一方资料及授权样本验证。

## 10. 加密库配置：不能只依赖 OpenList 默认值

所查 Crypt 参数默认文件名加密为 off、目录加密为 false，文件名编码默认 base64。[S3]

这不等于 v0.2 选择的“加密库媒体、封面及资料全部受保护”的完整配置。新加密库应明确选择内容及名称保护规则；同库配置在三端一致，不能只同步一个密码而忽略模式、salt、编码和根映射。

已有 Crypt 库必须匹配既有参数。不能为了符合新库默认值而修改老库配置，导致现有对象不可读。编码在 Windows/macOS 默认文件系统上的大小写/名称处理，仍需以实际暂存和导出方式验证。

指定普通目录并在界面选择“加密库”，不会自动把已有文件转换成密文。已有普通目录按普通库纳入、已有兼容密文按相同参数接入；普通与加密之间转换需要显式迁移流程，不隐式改写原件。

## 11. 对 PrivateVault 模块的直接影响

| 模块 | 必须处理的事项 |
|---|---|
| 账号/配置服务 | 凭证版本与设备刷新对账；中心暂不可用时已有设备按授权继续运行；不覆盖新凭证 |
| OpenListAdapter | 固定核心版本；明确官方访问路径、存储挂载、参数、必要请求头及实际错误含义 |
| 工作区/配额 | 显式覆盖 OpenList TempDir、完整密文暂存和工具原件；大文件先预留 |
| 任务状态 | 下载、加密准备、上传、验证和资料提交分开；重启后允许重传当前对象 |
| 播放 | 本机代理/解密、短期链接恢复、真正上游 Range 与编码兼容分别验证 |
| 元信息 | 保留明文尺寸、校验与验证等级；不把临时云链接或秘密作为长期资料 |
| 恢复材料 | 完整 Crypt 参数与库/路径映射；不包含无需备份的普通作品数据 |
