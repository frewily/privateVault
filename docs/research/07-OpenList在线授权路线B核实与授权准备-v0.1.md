## 1. 可以确认什么

1. 找到官方授权工具仓库 [OpenListTeam/OpenList-APIPages](https://github.com/OpenListTeam/OpenList-APIPages)，README 将 `api.oplist.org` 列为部署站点。
2. 匿名读取该站公开首页返回 HTTP 200，标题为 `OpenList Token`。只读取静态 HTML，没有运行页面脚本或调用登录/刷新接口。这不证明实际账号授权功能通过。
3. 百度分支支持使用服务端预设应用参数，用户不必为这条分支自行填写 AppKey/Secret。[S1][S2]
4. 代码中的授权、换取凭证和刷新均连接百度 OAuth；该中转服务没有在所查调用链上代替设备运行媒体下载、Crypt 或播放。
5. 本轮重新读取百度授权码和快速授权第一方正文，仍明确要求刷新令牌单次使用、保存新值，失败时不能反复重放旧值。[B1][B2]

因此可以继续收敛 B。**现成服务有完整的源码路径，不等于已经证明新授权与原挂载互不影响，或已经解决 PrivateVault 的多端凭证协调。**

## 3. 真实的授权与刷新链路

### 3.1 新授权

候选网页流程选择百度验证登录分支，并启用使用 OpenList 服务预设参数的选项；源码分支标识为 `baiduyun_go`、`server_use=true`。[S1][S5]

```text
用户在授权工具选择百度预设参数
    → 服务取得百度登录/授权跳转地址
    → 用户在百度页面登录并确认实际应用和权限
    → 百度授权码返回 OpenList 服务
    → 服务用预设应用参数向百度换取访问/刷新凭证
    → 浏览器显示结果，用户私下保管
```

源码请求的 scope 为旧授权方式的 `basic,netdisk`。这是请求值，不是用户账号已获得哪些权限的运行结论；实际应用名称、同意页和允许范围仍须在真实授权时确认。

新目录级快速授权使用不同的字段/端点。不能将其目录选择说明直接套成“当前预设应用必定只授权新测试文件夹”，也不能未经验证替换到现有驱动中。

本提案不选择 OOB 分支，不抄用其示例/内置第三方应用参数。

### 3.2 后续刷新

```text
测试设备持有的当前刷新凭证
    → api.oplist.org 的百度刷新入口
    → 服务携带其预设应用参数请求百度
    → 返回新的访问/刷新凭证
    → 调用设备保存最新值
```

所查 `genToken → pubRenew → Requests` 直接组织参数、转发请求并返回结果；没有在这条调用链看到设备注册、刷新互斥、凭证版本对账或向其他设备广播最新值的逻辑。[S1][S3]

该发现不等于完整部署不存在其他组件，但**不能把这个公开刷新接口当成 PrivateVault 的多设备凭证协调服务**。原有设计中的单一刷新所有者、版本同步和离线到期规则仍需处理。

### 3.3 回调信息必须私下处理

所查回调将访问/刷新凭证放入 Base64 编码的 JSON，再通过 URL 的 `#` 片段返回前端。前端读取后会尝试清除该片段。[S1][S4][S5]

Base64 是编码，不是加密；片段自动清除也不能替代保护措施。真实授权从登录到回调结果由用户本人操作，模型不截图、不读取该页 DOM、地址栏、剪贴板或回调链接。项目只记录成功/失败、应用名称和必要权限摘要，不记录令牌或原始错误正文。

## 4. 尚不能从公开资料保证的事项

| 问题 | 目前结论 | 对执行的影响 |
|---|---|---|
| 同一百度账号再次向该应用授权，旧授权是否继续有效 | 已读资料未给出明确并行独立性保证 | 不能承诺原挂载绝对不需要重新登录 |
| 把原刷新令牌复制到第二实例是否可独立刷新 | 官方单次使用规则不支持无协调复制的设计 | 不复制旧令牌；一个测试授权只交给一个百度驱动 |
| 新授权后原挂载暂时正常，是否证明长期独立 | 不能，访问凭证尚未到期可能掩盖后续刷新问题 | 不把立即可用写成多端验收通过，不故意让旧凭证失效验证 |
| 当前服务部署的应用身份、权限和配额 | 源码只显示从服务环境读取参数 | 实际应用以同意页为准；目录/配额仍是云测准备项 |
| 对原挂载的可能影响是否意味着会修改媒体 | 本轮没有发起文件 API，未观察账号行为 | 授权风险与媒体读写分开批准，不以未知推断文件已经改变 |

早先对多设备、重新授权问题的有限关键词检索没有得到结论。本轮已经找到并追踪官方 API 仓库，不再以“尚未找到源码”作为当前状态；剩余的是百度签发行为与实际服务配置，源码存在本身不能关闭这些问题。

## 5. 下一步具体提案：B0.1，一次受控新授权

**该步骤已获用户单独批准；用户反馈已保存，本机已确认接收完成标记和权限。** 用户私下授权结果尚未通过真实百度请求验证；不再次请求同一范围的许可，也不重新授权来补充应用名称。

建议将下一次范围限制为：

1. 先准备新的受保护本机临时接收位置和不回显的私下录入方式，仅保存本次测试凭证；需要的辅助工具只用于验证，不写产品实现。目录、文件权限与操作说明明确后，用户才开始授权，避免先生成令牌却无处保管。
2. 用户本人在官方授权工具完成最多一次百度预设参数授权。密码、扫码、同意页与回调由用户处理；不给模型密码、二维码、授权码、令牌或回调截图。
3. 实际应用与请求权限如不符合用户预期，停止；不切换其他应用参数、不反复尝试授权。
4. 新凭证暂不交给多个驱动，不填回原挂载，不在网页点额外的“刷新”来试验旧令牌。
5. 用户只报告授权成功/失败、实际显示的应用名称和必要权限摘要。原挂载登录状态仅依据用户正常使用反馈，不通过故意使旧刷新链失效来验证独立性。
6. 若原挂载出现登录异常，停止后续测试；保留新凭证供用户决定恢复方式，不自动反复授权、修改原配置或用旧备份覆盖轮换后的值。

**需用户明确接受的可能影响**：即使不复制旧令牌、不修改原配置，仍无法由现有公开资料保证再次授权不影响旧登录；原挂载可能需要用户重新登录。接受这一点后才能启动 B0.1，而不能以“隔离临时目录”承诺账号层面也已隔离。

B0.1 不启动云端上传，不创建/删除测试文件夹，不读取原收藏目录，也不启动旧 Desktop 或改系统设置。后续 B1 仍按方案 06 确认实际目录、配额处理、样本和执行范围。

如果用户暂不接受旧登录可能受影响，保持 B 作为选定路线，继续评估共享服务提供的授权规则或其他单一凭证所有者安排，不自动切换 A、申请自有应用或复制旧刷新令牌。

## 6. 对后续云测和产品的影响

- **云测目录隔离与 OAuth 权限不同。** 将测试挂载限制到专用目录能够约束测试操作，但不能声称百度授予的凭证只拥有该目录权限。
- **服务侧配额可能无法由用户查看。** B1 应如实记录未知项，并单独审阅低频、小样本、遇限额即停的探测范围；不把自有应用后台要求机械套到共享服务上，也不许诺精确请求总数。
- **凭证有效与归档成功不同。** B0.1 只处理接入；两个 PNG 的普通/Crypt 上传、读回及摘要属于 B1，视频/Range 属于 B2。
- **最终账号体验不变。** 保留独立 PrivateVault 账号恢复配置的方向；第三方服务的 app 参数托管不自动提供 PrivateVault 的用户账号、密钥同步和设备凭证协调。
